# ТЗ: перенос клиента Clayfolk на Godot 4 и объёмную графику

Дата: 19.10.2026. Исполнитель: Antigravity. Статус: задание подготовлено, перенос ещё не начат.
Исходная рабочая версия на момент составления: `c52f265` (проверить актуальный HEAD перед началом).

## 1. Что нужно получить

Работающий Windows-клиент Clayfolk на Godot 4: настоящий трёхмерный глиняный мир, фиксированная камера сверху под углом, объёмные персонажи со скелетными анимациями, единые свет и материалы. Сохранить непрямое управление поселением и существующие доступные механики. Новый клиент подключается к нынешнему авторитетному серверу Node.js/TypeScript.

Причина перехода — удобство дальнейшей разработки и согласованная графика. Выигрыш производительности измерять, не обещать заранее. Прототип с шариками вместо персонажей допустим только как промежуточная техническая проверка; он не является выполнением этого ТЗ.

Пользователь не обязан осваивать Blender, вручную собирать сцены или выполнять десятки операций в редакторе. Подготовка моделей, скелетов, материалов, анимаций, импорт и запуск входят в работу исполнителя. Код и файлы проекта должны воспроизводить результат без скрытых ручных действий.

### Принятые решения

- Godot 4 stable, обычная сборка, GDScript. Конкретную установленную версию зафиксировать в отчёте; не брать dev/nightly без обоснования.
- Blender для исходных 3D-моделей и анимаций, экспорт `.glb`/glTF 2.0. Версию Blender также записать.
- Основная платформа первого переноса — Windows x64. Браузерный экспорт не является критерием этого этапа; не обещать его совместимость с графикой ПК без отдельной проверки.
- Базовый рендер для ПК — Forward+. На этапе диагностики проверить поддержку GPU. Если оборудование требует другого режима, сначала записать ограничения и выбрать рабочий профиль, не скрывать потерю эффектов.
- Нынешние `server/`, `shared/` и клиент `client/` сохраняются. Godot размещается отдельно в `godot/`. Не удалять браузерный клиент до явного решения владельца проекта.
- Картинки текущей версии служат художественными референсами. Жители, здания и основные существа в новой версии — объёмные модели, а не повернутые к камере PNG-плоскости.

## 3. Границы и сохранность

Работать в отдельной ветке `codex/godot-3d-migration`; если она уже существует, проверить её состояние и продолжить без сброса чужой работы. Перед большими изменениями записать план по файлам и риски. Вести этапы небольшими коммитами; после проверенного этапа делать push в origin рабочей ветки. Не делать force-push и не сливать миграцию в main автоматически.

Не сбрасывать пользовательскую партию и обучение. Не удалять и не перезаписывать корневые `snapshot.json`, `.bak`, временные сохранения, `genome.json`, `genome-b.json`, `spider_genome.json` и другие фактически используемые файлы состояния. Эти локальные данные не добавлять в Git.

Для испытаний использовать отдельный сервер и отдельную папку состояния. Все переменные `SNAPSHOT_FILE`, `GENOME_FILE`, `GENOME_FILE_B`, `SPIDER_GENOME_FILE` задавать явно абсолютными путями; задать отдельный `PORT` (например 8788, если свободен). Проверить фактические имена в `config.ts`. Не запускать второй сервер с общими файлами сохранения.

Не отправлять `newGame`, `takeControl`, `setSandbox`, изменение скорости или другие игровые команды в текущую пользовательскую партию ради теста. При подключении нового клиента по умолчанию не захватывать управление автоматически: сначала получение состояния, затем явный выбор игрока.

Пользователь не заказывал переписывание серверной экономики, баланса, AI, миграций сохранения или внедрение новой сетевой платформы. Не переносить симуляцию в Godot и не заменять протокол Godot RPC. Если найдена настоящая серверная ошибка, отделить её от миграции, обосновать минимальное исправление и выполнить соответствующие серверные проверки.

## 4. Архитектура нового клиента

Рекомендуемая структура (имена внутренних файлов можно уточнить, разделение ответственности обязательно):

```
godot/
  project.godot
  export_presets.cfg
  scenes/           # world, resident, building, creatures, UI, visual lab
  scripts/network/  # WebSocket, decoder, commands, connection state
  scripts/world/    # registry by id, coordinates, interpolation, view model
  scripts/actors/   # resident/creature presentation and animation
  scripts/building/ # preview, brushes, parity rules
  scripts/ui/
  assets/models/    # imported GLB
  assets/materials/
  assets/animations/
  tests/fixtures/
  tests/
art/blender/        # editable .blend and reproducible generation/export scripts
scripts/godot/      # launch, isolated QA server, protocol fixtures, checks
docs/godot/         # setup, parity matrix, acceptance evidence, asset manifest
```

- Сеть, представление мира, анимации, интерфейс и инструменты строительства разделить. Не создавать один скрипт на несколько тысяч строк.
- В Git хранить проект, импортные настройки и исходники. Кэш `godot/.godot/`, временные Blender-backups, QA-сейвы, логи и экспортированные исполняемые файлы исключить из обычных коммитов. Не заменять редактируемый проект одним готовым EXE.
- Сопоставление координат: сервер `(x, y)` → Godot `(x, height, y)`. Базово одна серверная единица = одна единица Godot. Если нужен другой масштаб, единый коэффициент применяется ко всем координатам, footprints, кистям, свету и камере.
- Начало модели наземного объекта — в точке контакта с землёй. Масштаб тела и зданий принять на эталонной сцене; footprint для логики совпадает с серверным.
- Сервер остаётся единственным источником позиций, ресурсов, HP, задач, завершения стройки и исхода партии. Физика Godot не должна независимо толкать серверных жителей и создавать вторую симуляцию.
- Коллайдеры нового клиента нужны для выбора, наведения, лучей и визуальных тестов. Они не заменяют серверную валидацию маршрутов/построек.
- Объекты создавать/обновлять/удалять по стабильным ID. Не пересоздавать всю сцену и UI при каждом сетевом пакете.
- Король/королева как декоративное клиентское представление требуют отдельного адаптера существующих прогулок, безопасных маршрутов и сушки. Не добавлять от их имени серверных рабочих и не менять их экономику.

## 5. Сеть и совместимость

Транспорт — существующий WebSocket. Адрес задаётся настройкой/аргументом, по умолчанию локальный `ws://localhost:8787`; QA использует свой порт. Реализация должна работать с реальными пакетами текущего сервера.

- Сервер сразу присылает JSON объекта мира **на верхнем уровне**, без придуманной обёртки `world`/`payload`. Принимать текстовые JSON-пакеты.
- При несовместимой версии протокола показать понятную ошибку и не отправлять игровые команды. Не «чинить» сервер уменьшением версии.
- По сети племя в командах обозначается полем **`colony`**, хотя TypeScript-тип после парсинга содержит `colonyIndex`. Проверять `parseCommand`, а не копировать внутренний тип как wire format.
- Примеры: `{"type":"placeGate","colony":0,"x":40,"y":40,"axis":"horizontal"}`, `{"type":"setAlarm","colony":0,"value":true}`, `{"type":"setSpeed","value":1}`. В тестах координаты выбирать из валидной отдельной QA-карты.
- Не предполагать 60 сетевых снимков/с: сейчас рассылка ограничена `broadcastIntervalMs=100`. Интерполяцию строить на реальных временах получения и tick, с ограниченным буфером и задержкой отображения.
- Интерполяция не срезает стены, фундаменты и берега. Перенос соответствующих геометрических предикатов проверять общими JSON-fixtures, полученными из TypeScript-эталона. Не решать это новым самостоятельным поиском задач для жителей.
- Пауза, конец партии и потеря связи останавливают перемещение, шаг и рабочие циклы; декоративные атмосферные эффекты могут продолжаться отдельно.
- Уменьшение tick, смена мира/слоя, захват, спасение и настоящий телепорт очищают прежние траектории. Ускорение 20×/50× не считать телепортом только из-за большого смещения между пакетами.
- Ограничить накопление пакетов: при отставании не проигрывать всю устаревшую историю. Повторное подключение не дублирует людей, предметы и королевскую пару.
- Новые пакеты не должны повторно запускать один и тот же удар/выстрел. Данные shot/melee интерпретировать по текущим полям и срокам события.

## 6. Художественное направление и 3D-ресурсы

Образ: ожившая детская песочница из матовой глины, палочек, верёвок, камней и травы. Маленькие округлые персонажи с крупной головой, короткими полноценными руками и ногами. Тёплая терракота, мягкая шероховатость, небольшой рельеф лепки, понятные силуэты с игровой камеры.

Не нужны фотореалистичные люди, блестящий пластик, случайная смесь несовместимых наборов или тяжёлый кинематографический рендер. Красивый крупный рендер не заменяет читаемость модели в обычном игровом масштабе.

- Сначала один персонаж и один небольшой лагерь. Материалы, пропорции и освещение фиксируются в отдельной эталонной сцене.
- Полный персонаж: две ноги и руки, голова, глаза, пояс; королевские украшения отдельными объектами. Не собирать конечности из искажаемых фрагментов PNG.
- Глина жителей, домов, идолов и ресурсов принадлежит одной палитре. Для племени B сделать согласованную вариацию материала, а не случайный красный фильтр на всё, включая груз.
- Для каждой модели хранить `.blend` либо иной редактируемый исходник с достаточными правами, экспорт GLB и сведения об авторе/происхождении. Процедурные модели должны иметь запускаемый генератор и параметры.
- Готовые модели допустимы. Нужны доступные лицензии, совместимые с использованием в игре и хранением в этом репозитории. Покупки — только после явного согласования конкретного ассета и цены. При отсутствии прав на хранение исходников указать способ получения; не коммитить купленный пакет целиком без проверки условий.
- Не маскировать готовый плейсхолдер под финальную графику. В `ASSET_MANIFEST.md` указать статус: placeholder / authored / third-party / reviewed.
- Зафиксировать scale, origin, направления костей, имена анимаций и импортные настройки. Не оставлять внешние абсолютные пути к текстурам на машине автора.

## 7. Персонажи и анимации — обязательный критерий качества

Каждый житель использует нормальную 3D-модель, скелет и согласованные клипы. Наличие `AnimationPlayer` само по себе не считается готовой анимацией.

Минимальные состояния: idle; walk; carry_idle; carry_walk; добыча руками; axe_work; pick_work; build; melee; ranged; fishing; drying; hit; death/dissolve. Если несколько состояний используют общий клип, это должно визуально соответствовать занятию. Королевская пара использует ту же качественную походку, а не быстрое качание целого тела.

- В ходьбе обе ноги по очереди принимают опору и переносятся вперёд. Проверить спереди, сзади, справа, слева и с игровой камеры. Нельзя скрывать дефект удачным одним ракурсом.
- Поставленная стопа заметно не едет по земле в опорной части шага; ноги не разъезжаются, колени не выворачиваются, ступни не проваливаются. В стандартной лабораторной сцене ориентир: скольжение опорной стопы до 10% длины стопы за опорную фазу; измерять в мировых координатах, прикладывать также видео.
- Частота шага связана с реально отображаемой дистанцией. Позиция корня берётся из сервера/интерполяции, анимация не прибавляет к ней второй root motion. Длина шага и скорость клипа калибруются совместно.
- На ускорении отдельно ограничить читаемую частоту; не заставлять тело дрожать и не ускорять рабочие взмахи до нечитаемого состояния. На паузе сохраняется поза.
- Проверить slow/normal/fast и остановку: ¼× в лаборатории, 1×, 5×, 20×/50× в игре. Четвертная скорость сейчас не команда сервера; не менять сервер ради этой лабораторной проверки.
- Груз и инструменты крепятся к костям/сокетам. В обоих направлениях ресурс в руках, не на спине. Руки не проходят через крупный груз; венок следует голове без пульсации размера.
- Переходы между idle/walk/carry/work/attack без скачка масштаба, смены оттенка кожи и телепорта корпуса. Не имитировать шаг глобальным растяжением всей фигурки.
- При захвате пауком/жуком/монстром не оставлять свободную ходьбу и прежнюю леску. После освобождения сбросить захваченную позу.
- Не считать численную проверку стоп достаточным доказательством красивой анимации. Ранее именно такой подход дал испорченные ноги; нужна проверка целого силуэта в движении.

## 8. Земля, свет, вода и опора

- Земля объёмно и материально согласована с глиной. Дома имеют основание, контактное затемнение и мягкий переход к грунту: расчистка, мелкие камни, умеренные травы/цветы.
- Наземные объекты стоят основанием на поверхности. Тени рассчитываются в одном освещении, без жёстко нарисованной второй тени, противоречащей солнцу.
- Настроить дневной свет, переходы суток, ночь и локальный свет костров. Потухший костёр не освещает сцену. Не закреплять ночное освещение в albedo-текстуре.
- Костёр опирается камнями на грунт; огонь начинается среди поленьев, не висит над ними. Житель за костром правильно перекрывается и не оказывается в очаге из-за сглаживания.
- Следы ног привязаны к реальным шагам, постепенно исчезают; ориентир существующего клиента — пять на жителя, общий предел 800. Не увеличивать серверный снимок ради следов.
- У монстра разные наземная и плавательная анимации. В воде корпус погружён, видны спина/глаза, движение хвоста и рябь; он не проигрывает сухопутную ходьбу по поверхности озера. Переходы на берег согласованы с серверной позицией.
- Рыбы плавно поворачивают и плывут под водой. Рыболовная леска существует только при действующем забросе и обрывается при бегстве/захвате/уходе с места.
- Кувшинки лежат на воде; монстр на кувшинке имеет отдельную опору. Не менять серверную охоту, отдых и питание рыбой ради визуального упрощения.
- Убитый паук показывается тушей с мясом, а не кустом. В озере не возвращаются пунктиры смытой глины и цепочки остатков.

## 9. Паритет управления и механик

На этапе аудита создать `docs/godot/FEATURE_PARITY.md`: действие/состояние → исходный файл/команда → реализация Godot → доказательство проверки → статус. Для каждой строки статус implemented / partial / blocked / deferred с причиной. Старый недоступный функционал отделить от работающего, будущий roadmap не объявлять уже существующим.

Обязательный паритет доступной текущей игры:

- Панорама/зум/границы камеры, переход к лагерю, следование, выбор/наведение на жителей и объекты, понятные сведения о задаче и запасах, миникарта.
- Пауза, скорости 1/5/20/50, режим партии/песочницы, состояние соединения, смена управления A/B, цели и результат партии.
- Приоритеты clay/wood/stone/build/guard/fish, рост населения/резерв глины, тревога, пост обороны, доступное обучение водомётов.
- Зоны добычи и запрета, стирание, точечная постановка зданий, непрерывное рисование ограды, удаление стройки.
- Полупрозрачное **полное 3D-здание** нужного размера до подтверждения, валидность размещения и цена. Забор тянется видимыми секциями; Shift выравнивает линию. Ворота — одна постройка, поворот R, проход и занимаемые клетки соответствуют серверу.
- Правила земли/воды, костров, карьеров, зданий, своих/чужих ворот и предупреждения о перекрытии доступа согласованы с сервером. Сравнить Godot-предпросмотр с TypeScript на фиксированных fixtures; сервер остаётся последней проверкой.
- Видна вся существующая цепочка: добыча → переноска → склад → доставка материалов → строительство/ремонт → оборона. Дождь, намокание, сушка, растворение и гибель не исчезают при переносе.
- Два самостоятельных племени и развитие B, карьеры с конечными запасами и отдельными рабочими местами, рыбалка, монстры, нападения и финальные события отображаются из текущей симуляции.

Поведение не заменять локальной постановочной сценой. Все перечисленные действия в игровом режиме должны менять реальное состояние отдельного QA-сервера и переживать его сохранение/загрузку.

Внутренний редактор смещений старых 2D-спрайтов не переносить как обязательную игровую функцию: это технический инструмент прежнего рендера. Его отсутствие явно отметить в матрице. Предлагаемые новые функции и расширение многопользовательского режима вынести за границы переноса.

## 10. Этапы и выходные результаты

| Этап | Выполнить | Условие перехода |
|---|---|---|
| M0: аудит | Состояние Git, версии инструментов, текущие функции/протокол, план файлов, QA-папка, оборудование, матрица паритета | Есть конкретный план и способ не затронуть текущую партию; ограничения записаны |
| M1: визуальный образец | Один полноценный житель, ходьба/переноска/добыча, дом, костёр, земля, дневной и ночной свет, лаборатория движений | Реальные 3D и скелет; целый силуэт; четыре ракурса; видео ¼×/1×; нет очевидного скольжения и парения |
| M2: живой сетевой клиент | WebSocket, реальные snapshots, registry ID, координаты, интерполяция, пауза/ускорение/переподключение | Наблюдает реальный QA-мир; нет дублей, растущей очереди и второй симуляции |
| M3: управление | UI, камера, выбор, зоны, строительство, ограда, ворота и parity fixtures | Команды проходят существующий parseCommand; действия подтверждаются изменением серверного мира |
| M4: весь текущий мир | Остальные здания, ресурсы, карьеры, племена, правители, существа, вода/берег, бой, дождь, финал | В матрице нет необъяснённых пропусков обязательных функций; старые сохранения отображаются корректно |
| M5: качество и поставка | Регрессии, длительный прогон, настройки качества, Windows export, воспроизводимый запуск и handoff | Полный комплект доказательств, исходников, инструкций; проверенные коммиты отправлены в origin |

Не откладывать персонажа и качество походки до конца массового переноса. M1 оформить отдельным коммитом и показать короткое видео — это первая точка художественной обратной связи. При получении замечаний пользователя учесть их до тиражирования моделей. Отсутствие ответа не считать художественным одобрением; можно продолжать независимую сетевую часть.

Не останавливать работу после одного отчёта/плана, пустой сцены или успешной компиляции. Продолжать по этапам до рабочего результата; конкретное внешнее препятствие описать с уже выполненными попытками и способом продолжения. Не требовать от пользователя рутинных действий в Blender вместо подготовки воспроизводимого проекта.

## 11. Проверка и производительность

### Автоматические проверки

- Существующий `npm run check`; после серверных/общих изменений также `npm run check:slice` и затронутые профильные проверки.
- Навигация/ограда/вода: `check:navigation`, `check:fences`, `check:grounding`; экономика/депозиты: `check:gameplay`, `check:deposits`; дрожание/движение: `check:jitter`, `check:motion`. Не запускать все длинные проверки после чисто художественной правки без причины.
- Godot: headless import/check проекта, тестовый runner для декодера snapshots, wire-команд, registry, преобразования координат, паузы/переподключения и общих geometry fixtures. Конкретные команды и коды возврата записать после появления файлов, не выдумывать несуществующие готовые скрипты.
- Нельзя заменить Godot-тесты успешными тестами старого TypeScript-рендера. Старые motion/grounding проверки подтверждают лишь соответствующую существующую реализацию.

### Обязательная проверка в запущенной игре

1. Новая отдельная партия и копия существующего сохранения; оба племени; одинаковые количества объектов/материалов на сервере и в UI клиента.
2. Добыча/доставка глины, дерева, камня и еды; несколько работающих жителей в карьере; истощённый узел не выглядит полным после перезагрузки.
3. Строительство четырёх типов зданий, ограды и ворот обеих ориентаций; вход/выход, встречный поток, стройка вплотную к препятствию, недоступная установка.
4. Медленная и обычная ходьба с грузом/без, четыре направления, поворот, остановка у препятствия, правители; пауза и 50×.
5. День/ночь, горящий/потухший костёр, дождь/сушка, повреждение и растворение. Нет тел под огнём и проваливающихся ног.
6. Рыбалка, бегство, захват/спасение, монстр в воде/на берегу/на кувшинке, гибель паука, видимый бой.
7. Перезапуск клиента, потеря/восстановление связи, сохранение/перезапуск QA-сервера, новая партия и исход матча. Нет повтора старых ударов и дубликатов.
8. Не менее 30 минут реального наблюдения QA-сцены с меняющимися задачами/строительством; ускоренный прогон дополнительно, не вместо проверки движения при 1×.

### Цели нагрузки

- До измерений записать CPU/GPU/RAM, разрешение, Godot renderer и профиль качества. Не выдавать headless-время симуляции за FPS клиента.
- Цель обычной сцены: около 60 FPS при 1920×1080 и 100 видимых жителях на зафиксированном тестовом ПК. Это приёмочная цель, а не заранее доказанная характеристика любого компьютера.
- Отдельные stress fixtures: 50/100/300/500 жителей, груз, бой, следы, дождь и тени. Для каждого дать средний FPS, p95 времени кадра, использование памяти и замечания после прогрева. При 300/500 допустимо снижение качества по явно описанному профилю; нельзя тайно уменьшать число жителей или останавливать их симуляцию.
- Использовать общие meshes/materials, инстансы окружения, ограниченные тени/частицы/следы, LOD по необходимости. Не ставить каждому жителю отдельный полноценный AI/поиск пути или независимый динамический источник света.
- При провале цели найти основной расход и записать измеренный результат. Не называть этап оптимизированным по факту перехода на движок.

## 12. Что передать для последующей проверки Codex

1. Рабочую ветку, hash последнего проверенного коммита, push в origin; чистый Git либо явный список незавершённых файлов.
2. `godot/project.godot`, все необходимые сцены/скрипты, редактируемые 3D-исходники и GLB, manifest происхождения/лицензий, без локальных сейвов и секретов.
3. `docs/godot/SETUP.md`: точные версии, инструменты, один понятный запуск сервера и клиента, отдельный QA-запуск, export/build. Автозапуск не должен убивать чужой сервер или занимать его порт без проверки.
4. `docs/godot/FEATURE_PARITY.md`, `ACCEPTANCE.md`, `PERFORMANCE.md`; ссылки на исполняемые тесты и их последние результаты, без вымышленных PASS.
5. Короткие записи игры: ходьба/переноска четырёх направлений, рабочие/строительство/ворота, ночь/дождь, вода/монстр/бой. Записи из Godot, не рендер Blender и не старый браузерный клиент.
6. Изменения protocol/shared/server объяснить отдельно. Доказать, что пользовательское сохранение и старая версия клиента не сломаны.
7. Известные дефекты и ограничения с воспроизведением, приоритетом и предлагаемым следующим шагом. Не переносить основные неработающие механики в раздел «Codex потом доделает».

Код и картинки в репозитории — не единственный критерий. Приёмка требует запуска, сохранённой игровой петли, читаемой анимации, согласованного визуального мира и проверяемых доказательств. Финальное художественное одобрение остаётся за пользователем.
