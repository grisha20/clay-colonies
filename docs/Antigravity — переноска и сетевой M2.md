# Antigravity — переноска и сетевой M2 после defc128

Прочитай `AGENTS.md`, основное ТЗ переноса, `docs/GODOT_MIGRATION_STATUS.md` и `docs/godot/M1_REVIEW_defc128.md`. Продолжай текущую ветку `codex/godot-3d-migration`, без reset/force-push/слияния в main. Сначала проверь Git: работа могла продолжиться после этого задания.

## Что уже проверено

defc128 исправляет потерю весов ног: 0/1326 без весов, импортированные подошвы связаны с Foot.L/R и реально движутся. Независимая проверка контакта <0,8 мм; 8 grounding + 8 rigor + 10 QA проходят. Не переделывай исправленные ноги, не откатывай модель к ba300ea и не заменяй измерения реальных вершин формулой щиколотки.

Полный M1 ещё не принят: груз и руки погружаются в живот, у плеч видны выступающие плоские торцы. Художественное одобрение пользователя не получено. По §10 основного ТЗ это допускает независимую сетевую работу, но не массовое тиражирование нового визуального стиля.

## 1. Ограниченная доработка переноски

Сначала план по файлам и рискам. Основные места: `art/blender/generate_resident.py`, при необходимости генератор груза, экспортированные blend/GLB, `godot/scripts/actors/lab_resident.gd` и лабораторные проверки.

- В `carry_idle` и `carry_walk` груз должен читаться перед животом, а кисти — охватывать его по бокам. Проверяй деформированную поверхность рук и контур корпуса, не только расстояния между костями и наличие сокета.
- Исправь положение сокета/позу/форму рук с учётом нынешнего объёма торса. Простой большой вынос груза, оставляющий кисти внутри тела, не решает задачу. Не делать прозрачным тело и не отключать depth test ради видимости.
- Убери выступающие торцы у плеч. Сохрани нулевую потерю весов и текущую опору ног. Не расширяй этот пункт до переделки всех персонажей/построек.
- Свежие кадры фронт/профиль/игровая камера для idle-переноски и полного цикла carry_walk, плюс короткий GPU-клип. Проверка должна падать при намеренном возвращении груза внутрь корпуса, а не только при удалении BoneAttachment.
- Прогони текущие grounding/rigor и headless import. Отдельный проверенный commit + push.

## 2. Подготовить реальное изолированное QA для M2

Сохранить существующие lock/staging/token-защиты. В `scripts/godot/qa_server.py` и его тестах подтвердить настоящим Node/tsx-сервером:

- валидный fixture создаётся/получается средствами текущего сервера, загружается без молчаливого создания новой партии; tick, племена и контрольные сущности подтверждаются полученным WebSocket snapshot;
- штатное завершение и ошибка процесса дают корректный exit code; остановка собственного дерева Node/tsx освобождает порт и lock; новый запуск из той же QA-папки работает;
- текущие корневые `snapshot*`, `genome*`, `spider_genome*` не используются и не изменяются. Все четыре state-пути и порт заданы явно. Источник fixture лежит вне изменяемой state-папки;
- при недоступном порте/невалидном fixture/живой блокировке запуск прекращается до изменения состояния. Не убивать уже работающий чужой сервер.
- отдельный отрицательный тест: release с чужим токеном не снимает живую блокировку владельца.

Python-тест дерева с TCP-потомком уже есть, повторно выдавать его за новый Node integration test нельзя. Не подменять настоящее сохранение сетевой JSON-проекцией или Python-заглушкой.

## 3. M2 — наблюдающий сетевой клиент

Перед реализацией запиши небольшой план файлов: подключение/декодер в `godot/scripts/net/`, registry и отображение в `godot/scripts/world/`, отдельная игровая сцена, воспроизводимые тесты/fixtures. Имена можно выбрать по существующей структуре. Не переписывать server/shared/client и не переносить симуляцию в Godot. Лабораторию оставить доступной отдельно.

Выполни сетевые требования основного ТЗ:

- `WebSocketPeer`, настраиваемый адрес, по умолчанию `ws://localhost:8787`; проверки только на отдельном QA-порту. Читается верхнеуровневый JSON мира. Версию сверить по текущему коду; несовместимость показывать понятно, без игровых команд.
- Подключение изначально наблюдающее: никаких автоматических `takeControl`, `newGame`, смены скорости/паузы или иных команд текущей партии. Сценарии скорости/паузы разрешены только на проверенном отдельном QA-сервере.
- Registry по стабильным ID. Жители из верхнего `ants`, разделение по `colonyId`; обновление/удаление без полного пересоздания сцены на пакет. Для других типов мира на M2 достаточно честного базового представления и счётчиков; весь арт относится к M4.
- Координаты мира и масштаб едины. Интерполяция учитывает реальные времена пакетов/tick, ограниченный буфер, паузу, потерю связи и резкие изменения. Не накапливать бесконечную очередь и не выполнять локальный AI/поиск пути.
- Не срезать здания, заборы и берег. Сверять нужные предикаты с общими fixtures из TypeScript; при невозможном безопасном переходе использовать документированный способ восстановления, а не прохождение сквозь препятствие.
- Частота шага связана с реально отображаемой пройденной дистанцией и масштабом, а не со временем с момента запуска. Сохранять чередование ног при остановке, поворотах и переноске. Гарантии лабораторной прямой не считать доказательством качества сетевой интерполяции.
- Проверить 0/1/5/20/50×, нестабильную доставку пакетов и переподключение. На паузе положение/поза стоят. На высокой скорости нет неограниченного отставания от мира; ограничения частоты анимации и переходов описать честно.
- После disconnect статус видим, старые сущности не продолжают бесконечно идти. Reconnect не создаёт дублей и удаляет исчезнувшие ID.

## 4. Приёмка и отчёт

Автотесты: декодер реальных пакетов и невалидных входов, версия, registry create/update/remove, координаты, буфер/пауза, reconnect. Интеграционно два запуска: новая QA-партия и копия валидного существующего QA-сохранения. Количества/ID и оба племени сверить с сервером. Браузерная игра продолжает работать отдельно.

GPU-видео нового клиента с реально движущимися серверными жителями, грузом, остановкой и сменой направления; сценарий с постройкой/оградой/водой, разрывом связи и восстановлением. Контроль движения при 1× обязателен. Не выдавать локальный тур лаборатории за подключение к миру или offline Movie Maker за измерение FPS.

Обновляй status/acceptance по фактам, сохраняй прошлые аудиты. По каждому проверенному этапу commit + push. В финале: SHA, команды и exit codes, QA-пути/порт, как запустить наблюдающий клиент, медиа, оставшиеся ограничения. Если один пункт блокирован, опиши конкретную причину и продолжай независимые пункты. M3–M5 не объявлять готовыми авансом.
