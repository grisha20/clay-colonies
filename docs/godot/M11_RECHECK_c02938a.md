## Что ещё не подтверждено / не исправлено

### P1. Stale-lock recovery может отобрать блокировку у нового живого владельца

Обычный конкурентный захват теперь действительно использует подготовленный каталог и атомарный rename. Прежняя гонка создания пустого lock закрыта. Однако `scripts/godot/qa_server.py:140–143` принимает решение по прочитанному старому PID, затем переносит **текущий каталог по тому же имени** без проверки, что это всё ещё прочитанный владелец.

Воспроизведён сценарий на временном каталоге: A и B прочитали одну старую блокировку с мёртвым PID; A убрал её и получил новую; задержанный B по старому решению переименовал и удалил уже живую блокировку A, затем тоже успешно получил каталог. Результат — **два успешных владельца**. Семь тестов этого порядка событий не проверяют. Решение: безопасный протокол восстановления с проверяемым владением/системной блокировкой либо отказ от автоматического удаления неоднозначной старой блокировки. Не подменять это ещё одной проверкой `exists`.

`release_state_lock` также узнаёт владельца только по PID и удаляет каталог без owner.json; это не уникальный токен конкретного захвата. При исправлении учесть освобождение чужого/сменившегося владения.

### P1. Ошибка записи fixture уничтожает предыдущее QA-состояние

Запрет fixture внутри state-dir теперь закрывает прежнюю потерю источника `.bak/.tmp`: этот пункт исправлен. Но `qa_server.py:290–298` сначала удаляет прежний snapshot и резервные файлы, затем пишет новое содержимое прямо в snapshot. «Stage» означает только JSON в памяти, не подготовленный файл.

На временных данных и с подставленной ошибкой открытия целевого snapshot воспроизведено: `OSError('simulated fixture write failure')`, старое QA-состояние уже удалено. Настоящий сервер не запускался. Требуется временный файл + проверенная запись/закрытие до замены назначения, и сохранение прежнего состояния при отказе. Обработку сбоя записи тестировать отдельно от preflight.

### P2. Приёмка QA lifecycle и пригодности fixture заявлена шире тестов

Все 7 тестов — preflight, схемы и locks; ни один не запускает дочерний сервер, не проверяет его ненулевой выход/осиротевшее дерево и загрузку реального положительного fixture. В `start_server` cleanup по-прежнему вызывает kill только пока parent жив. При самостоятельном выходе родителя с живым потомком обнаружение занятого порта возвращает ошибку, но не доказывает остановку собственного дерева.

Валидатор теперь проверяет типы версии/tick/surface и массивов colonies/ants; прежний пример `tick:"not-a-number"` отвергается. Однако позитивный тест всё ещё использует сокращённый объект без обязательных `colonies[].colony.population`, а загрузчик `worldFromSnapshot` обращается к ним непосредственно. Положительная загрузка и сохранность при ошибке должны быть доказаны на изолированном окружении; отметка «полностью безопасен» преждевременна.

### Художественная часть остаётся незавершённой

Новый реальный профиль и свежий GPU-кадр переноски показывают:

- плечи/локти/колени выглядят как отдельные жёсткие детали с выраженными стыками;
- на голове заметна граница назначения двух материалов, а не только плавное освещение;
- пояс сделан отдельными бусинами; ступни имеют прямоугольное основание;
- фактура лепки почти не читается, грунт однородный, дом остаётся очень простым цилиндром с конусом.

Это субъективная оценка стиля, подкреплённая конкретными видимыми признаками, **не повторное отрицание исправленной кинематики**. Изначальная цель M1 — приятный глиняный образец в стиле текущих референсов, а не только правильный скелет. Одобрения владельцем нет. Следующий художественный проход должен менять фактическую модель/материалы, а не формулировки отчёта.
